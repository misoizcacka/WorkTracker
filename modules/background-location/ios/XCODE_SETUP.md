# iOS Native Module — Xcode Setup Checklist

Before you run an EAS production build, you need to configure three things in Xcode.
This is a one-time setup. All code changes are already done.

---

## 1. App Group Capability

Both `TrackingStateStore` and `LocationDbHelper` use the App Group identifier:

```
group.app.koord.tracking
```

**Steps:**
1. Open `frontend/android/` → no, open the iOS project in Xcode:
   `frontend/ios/Koord.xcworkspace`  (generated by EAS / `expo prebuild`)
2. Select the **Koord** target → **Signing & Capabilities** tab
3. Click **+ Capability** → choose **App Groups**
4. Add the group: `group.app.koord.tracking`
5. Repeat for any Extension target if you add one later

Without this, the module falls back to standard `UserDefaults` (state may not survive a process kill) and the DB uses the Documents/SQLite fallback path. The app still works — it's just less resilient.

---

## 2. Background Task Scheduler Identifier

`IOSBackgroundLocationManager` schedules a `BGAppRefreshTask` with identifier:

```
app.koord.location.refresh
```

**Steps:**
1. In Xcode, select the **Koord** target → **Info** tab (or edit `Info.plist` directly)
2. Add the key: `BGTaskSchedulerPermittedIdentifiers`  (type: Array of String)
3. Add one item: `app.koord.location.refresh`

You can also add this in `app.config.js` under `ios.infoPlist`:

```js
ios: {
  infoPlist: {
    // ... existing keys ...
    BGTaskSchedulerPermittedIdentifiers: ['app.koord.location.refresh'],
  }
}
```

Without this, `BGTaskScheduler.shared.submit(request)` throws silently and the
background refresh chain never starts — location tracking still works while the
app is in the background, but events may not flush if the app is fully suspended.

---

## 3. Background Modes Capability

Required for `CLLocationManager.allowsBackgroundLocationUpdates = true` and `BGAppRefreshTask`.

**Steps:**
1. **Signing & Capabilities** → **+ Capability** → **Background Modes**
2. Check:
   - ✅ **Location updates**
   - ✅ **Background fetch** (required for BGAppRefreshTask)

These are already declared in `app.json` under `ios.infoPlist.UIBackgroundModes: ["location"]`.
The "Background fetch" mode needs to be added:

In `app.json` → `ios.infoPlist`:
```json
"UIBackgroundModes": ["location", "fetch"]
```

---

## 4. Location Usage Descriptions (Already Done)

These are already in `app.json`:
- `NSLocationWhenInUseUsageDescription`
- `NSLocationAlwaysAndWhenInUseUsageDescription`
- `NSLocationAlwaysUsageDescription`

No action needed.

---

## 5. Notification Permission

The module shows a persistent notification when a work session is active (mirrors Android).
Notification permission is already requested in `home.tsx` via `Notifications.requestPermissionsAsync()`.

**Important:** The notification shown by the native module uses `UNUserNotificationCenter`,
which requires the user to have granted notification permission. If they denied it, the
tracking still works — they just won't see the "Working at X" notification.

---

## Summary of what changes when App Group is NOT configured

| Feature | Without App Group | With App Group |
|---------|-------------------|----------------|
| State after process kill | May be lost (standard UserDefaults) | Persisted (App Group UserDefaults) |
| DB path | Documents/SQLite/workhourstracker.db | AppGroup container/SQLite/workhourstracker.db |
| Geofence recovery on relaunch | Partial | Full |

For initial testing without an Apple Developer account (simulator), everything works
via the fallback paths — you can verify the logic without the App Group.
